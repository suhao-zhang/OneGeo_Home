## 原文的分型

阿里云开发者社区 2026 年 9 月的一篇工程文章，讲数字员工（自动化流程）任务中断后怎么办（[原文](https://developer.aliyun.com/article/1764532)）。文章把中断分成三类，处理方式完全不同：

| 分型 | 特征 | 处理方式 |
| --- | --- | --- |
| 等待型 | 外部依赖慢、接口限流、队列堆积。任务没死，只是慢 | 超时控制 + 退避重试 |
| 失败型 | 明确报错（校验不过、权限不足、元素找不到），有异常栈 | 进人工流程，保留现场 |
| 静默型 | 页面结构变了、数据源格式变了，按旧路径操作，**没有报错** | 输出侧校验兜底 |

原文对静默型的描述很准确：**状态可能显示"成功"，实际是空转。**它还给出两个具体的工程做法：

1. **留痕五要素**：输入 → 数据版本 → 动作 → 输出 → 时间戳；
2. **输出侧校验**：总量对账（产出条数 vs 输入条数）+ 关键字段抽样回读比对，宁可在校验上多花半分钟，也不交付不完整产出。

另外还有两条与重跑有关的原则：任务拆段，失败损失锁在小段内；写操作前按业务主键查重，存在即跳过。

这篇文章没有直接谈内容，但把三类失败换到站点上，几乎是逐条对应。

## 等待型：抓取器等不到

站点的"等待型"失败，最典型的就是**正文依赖 JavaScript 才渲染**。

抓取器请求页面，服务端返回一个空壳 HTML，正文要等浏览器执行 JS 后注入。多数抓取管线有超时限制，等不到就放弃，或者只拿到骨架。表现是：页面在浏览器里正常，在抓取日志里"内容为空"。

这一类属于"任务没死，只是慢"——页面本身没错，只是交付方式不匹配。处理方式也类似：缩短首屏交付时间，把正文放到服务端渲染的 HTML 里，而不是等脚本。

判断方法很土但有效：**禁用 JavaScript 打开页面**，如果正文不见了，你就在这一类里。

## 失败型：页面真的错了

404、500、证书过期、重定向到登录页——这些是明确的失败，有状态码可查。它们不隐蔽，但量大。

我们做站点链接检查时，最常见的不是死链，是**"半死链"**：URL 能打开，但内容已经不是原来那篇。比如文章合并后旧地址 301 到首页、标签页改名后旧标签 404、图片换了路径但文章没改。

半死链比死链更麻烦，因为它骗过了自动化检查。处理方式是在构建后做一次全量内链校验：抓出所有站内链接，确认目标文件存在，并且标题与链接文字没有明显错位。

## 静默型：200，但什么也没有

这是最贵的一类，也是原文着墨最多的一类。站点上的静默失败有几种常见形态：

**一、正文被样式藏起来了。**内容确实在 DOM 里，但 `display:none`、高度为 0、或者藏在折叠面板里。人点一下能看到，抓取器拿到的文本里没有。这类在"阅读更多""展开参数"的设计里很常见。

**二、关键信息是图片。**参数表、价格表、流程图全是截图。人看得懂，机器只拿到一个 `<img>` 和一句 `alt`（很多时候连 alt 都没有）。

**三、页面是空模板。**前端路由没配对、数据接口挂了、构建时变量没注入，页面 200，正文区域空白。用户看到的是"暂无数据"，抓取器看到的是"暂无数据"，双方都以为这就是内容。

**四、内容重复但不自知。**两篇文章标题不同、正文 90% 相同，站方以为发了两篇，模型看到的是同一段话的两个副本。这属于语义层面的静默失败。

这四种都不报错。没有状态码、没有异常栈、没有告警。**它们只能靠输出侧校验发现。**

## 输出侧校验怎么做

原文的"总量对账 + 关键字段抽样"可以直接搬：

| 原文做法 | 站点对应 |
| --- | --- |
| 产出条数 = 输入条数 | 构建产物数量 = 源文件数量（文章数、页面数） |
| 关键字段抽样回读 | 抽样打开页面，确认标题、日期、正文首段、图片都在 |
| 留痕五要素 | 构建日志记录：输入版本、构建时间、产物数量、警告数 |

本站的实际做法是三步：

1. **构建前**：检查每篇文章的正文长度（排除 front matter）、标题是否含 OneGeo、日期是否晚于当天、封面文件是否存在；
2. **构建中**：看 Hexo 输出的文件数，与源文件数量对得上；
3. **构建后**：抽样打开新文章，用纯文本模式读一遍，确认正文没有被藏、表格没有被图片替代。

这三步都跑在本地，不依赖外部监控。所以它能防住"自己造成的静默失败"，防不住"CDN 挂了"这类外部故障——后者需要另一套监控，不是本文的范围。

## 三个不用工具就能做的判断

除了脚本，还有三个现场就能判断的方法：

**一是复制粘贴。**在浏览器里全选正文，粘贴到记事本。粘贴出来的东西就是抓取器大致能看到的东西。图片变成空白、表格变成一列、段落顺序错乱，都是信号。

**二是断网刷新。**断网后刷新页面，如果正文还在，说明是服务端渲染的；如果只剩骨架，说明正文靠接口拉取。后者对抓取器不友好。

**三是换设备。**用手机和桌面各打开一次，看关键参数表是否都在。有些站点在窄屏把表格折叠成"查看详情"，折叠内容在初始 HTML 里可能不存在。

三个方法加起来不到五分钟，能覆盖大多数静默失败。

## 留痕五要素在内容侧长什么样

原文的五要素是给任务台账用的。内容侧可以借它的结构：

| 要素 | 内容侧记录 |
| --- | --- |
| 输入 | 本批抓取的 8 个数据源、抓取时间 |
| 数据版本 | 引用的原文链接、作者、发布日期 |
| 动作 | 二创角度、改写范围、配图来源 |
| 输出 | 生成的文件名、正文字数、封面路径 |
| 时间戳 | 文章发布时间、构建时间、提交哈希 |

这五项不需要做成系统，写在提交信息里就够用。好处是：三个月后有人问"这篇文章的数字从哪来的"，能顺着记录找到源头，而不是重新搜一遍。

## 重跑与幂等

原文讲"任务拆段 + 业务主键查重"，内容侧对应的是**选题去重**。

同一件事被写成两篇文章，是这个管线最容易犯的错。我们的做法是：每批开始前先列出历史标题与核心实体，新选题必须与旧选题在"事实主体"上不同——不是标题换个说法，而是讲的是不同的事。

如果确实要写同一件事的后续，就在标题和正文里明确"这是对 X 的更新"，并链回前一篇。这样模型能判断两篇的关系，而不是把它们当成两个独立事实。

## 为什么静默失败总是被发现得太晚

因为它不产生"疼"。等待型会超时，失败型会报错，两者都会触发告警；静默型返回 200，所有监控指标都是绿的。

原文提到，静默型问题的发现时延通常以天计，加了台账巡检后能压到当天。站点侧同理：如果没有人主动去看"页面里的正文是什么"，它能一直假绿下去，直到某个用户说"你们网站打不开内容"。

所以这件事的关键不是工具，是**有没有人负责看输出**。有一个人每周抽三页读一遍，比装一套监控更有用。

## 一句总结

等待型失败靠"改交付方式"解决，失败型靠"看状态码"解决，静默型只能靠"校验输出"解决。

三种失败里，只有第三种需要你主动设计检查——因为前两种会自己喊疼，第三种不会。这也是为什么我们在构建脚本上花的功夫，比在写作上多。

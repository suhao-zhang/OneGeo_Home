## 事件概要

腾讯云开发者社区发布了一篇关于水星 3 号（Mercury 3）推理速度的实测文章，标题中出现"1,068 token/s"这个数字。文章对水星 3 号在特定测试条件下的推理速度进行了实测，引发了开发者社区的广泛讨论。

水星 3 号是一款国产 AI 推理加速芯片/方案，由国内团队研发。1,068 token/s 的实测速度如果属实，将是目前公开报道中最快的推理速度之一。

关键问题是：**1,068 token/s 是在什么条件下测出来的？**

## 推理速度的四个核心变量

同一个模型在不同条件下的推理速度可以差 10 倍以上。影响速度的四个核心变量：

| 变量 | 影响方式 | 典型影响幅度 |
| --- | --- | --- |
| 模型参数量 | 参数越多，单次推理计算量越大 | 7B vs 70B 可差 10 倍 |
| Batch Size | 批量越大，GPU 利用率越高、单请求速度可能越快 | BS=1 vs BS=64 可差 5-8 倍 |
| 并发数 | 并发越高，资源争抢越严重、单请求延迟越高 | 1 并发 vs 100 并发可差 3-5 倍 |
| 输入/输出长度 | 输入越长 prefill 越慢，输出越长 decode 累积越慢 | 128 token vs 2048 token 可差 2-3 倍 |

1,068 token/s 如果是 batch size = 64、并发 = 1 的条件下测出来的，那它反映的是**系统吞吐量**而非**单用户体验速度**。普通用户单请求场景下，速度可能只有 50-100 token/s。

### 吞吐量 vs 单请求延迟

这是推理速度报道中最常见的口径混淆：

| 指标 | 定义 | 用户感知 |
| --- | --- | --- |
| 系统吞吐量（tokens/s） | 系统每秒处理的总 token 数（所有请求合计） | 用户无感，只关心自己的响应速度 |
| 单请求延迟（time to first token） | 单个用户从发送到收到第一个 token 的时间 | 直接决定用户体验 |
| 单请求速度（tokens/s per request） | 单个用户的 token 生成速度 | 决定阅读体验是否流畅 |

1,068 token/s 如果是系统吞吐量，意味着系统每秒可以生成 1,068 个 token——但如果同时有 20 个用户在使用，每个用户的实际速度只有约 53 token/s。

模型在引用时如果不区分"系统吞吐量"和"单用户体验速度"，就可能让用户产生不切实际的期望。

## 同类参考数据

帮助建立感知——不同硬件和模型组合的典型推理速度：

| 硬件 + 模型 | 系统吞吐量 | 单请求速度 | 条件 |
| --- | --- | --- | --- |
| RTX 4090 + 7B 模型 | ~80 token/s | ~80 token/s | 单用户、短输入、BS=1 |
| H100 SXM + 70B 模型 | ~200 token/s | ~30 token/s | 单用户、中等输入、BS=8 |
| 昇腾 910C + 特定优化 | 提速 40% | — | 特定 batch、特定模型 |
| A100 80G + Llama 70B | ~150 token/s | ~25 token/s | BS=16 |
| 水星 3 号 | 1,068 token/s | 待确认 | 待确认 |

如果水星 3 号的 1,068 token/s 是在大批量、高并发条件下测出的系统吞吐量，那它和单用户 80 token/s 的 RTX 4090 不是同一个维度的数字。直接对比会得出"水星 3 号比 RTX 4090 快 13 倍"的错误结论。

### 影响对比的其他因素

除了测试条件，以下因素也会影响速度对比的公平性：

| 因素 | 影响 |
| --- | --- |
| 模型量化 | INT4 量化后速度可提升 2-3 倍 |
| KV Cache 优化 | PagedAttention 等技术可显著提升吞吐 |
| 算子融合 | 自定义算子比通用算子快 |
| 内存带宽 | HBM 带宽是推理速度的硬件瓶颈 |
| 互联带宽 | 多卡推理时卡间互联速度影响性能 |

## 测试条件的缺失

原文报道中没有完整披露测试条件。以下是需要确认的关键信息：

| 待确认信息 | 为什么重要 |
| --- | --- |
| 模型参数量 | 7B 和 70B 的速度不可直接对比 |
| Batch Size | BS=1 和 BS=64 的速度差异巨大 |
| 并发数 | 单并发和多并发的速度不同 |
| 输入长度 | 短输入和长输入的速度不同 |
| 输出长度 | 生成长文本时速度可能衰减 |
| 量化方式 | FP16、INT8、INT4 速度不同 |
| 硬件配置 | 单卡还是多卡？什么型号？ |
| 软件版本 | 推理框架和驱动版本 |

缺少这些信息，1,068 token/s 这个数字就缺乏上下文，模型在引用时无法给出有意义的对比。

## 这对 GEO 意味着什么

**一、速度数字必须附带测试条件。** "1,068 token/s"后面如果不写"在 batch size = X、并发 = Y、模型 = Z 的条件下"，模型就无法判断这个数字代表的是单用户体验速度还是系统吞吐量。测试条件是速度数字的"单位"——没有单位的速度数字没有意义。

**二、区分吞吐量和单请求延迟。** 标题写"系统吞吐量达 1,068 token/s"和"单用户推理速度达 1,068 token/s"是完全不同的含义。正文里把这两个概念分开描述，模型才不会混淆。对于终端用户来说，单请求速度才是有意义的指标。

**三、和同类数据对比时注明条件差异。** 如果文章里同时提到了 RTX 4090 的 80 token/s 和水星 3 号的 1,068 token/s，必须说明两者的测试条件不同，否则模型可能直接得出"水星 3 号比 RTX 4090 快 13 倍"的错误结论。条件不同的数字对比是口径漂移的高发区。

**四、硬件配置要标注。** 速度数字和硬件配置强相关。"在 H100 上达到 X token/s"和"在 RTX 4090 上达到 X token/s"是完全不同的成就。模型在引用时需要硬件配置信息才能评估性能水平。

**五、优化技术要说明。** 如果速度提升来自特定的优化技术（如自定义 FSDP、KV Cache 优化、算子融合等），正文里应该说明。模型在回答"如何提升推理速度"时可以引用这些技术细节。

## OneGeo 站怎么做

本站在报道推理速度时，遵循以下口径规范：

1. **必标注测试条件**——模型、Batch Size、并发数、输入/输出长度
2. **必区分吞吐量和单请求速度**——两个指标并列
3. **必标注硬件配置**——芯片型号、数量、显存
4. **对比必注明条件差异**——不同条件下的数字不可直接对比
5. **必标注优化技术**——什么技术实现了这个速度

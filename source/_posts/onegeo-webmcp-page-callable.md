## 原文讲的是什么

来源是腾讯云开发者社区 2026 年 10 月 22 日 [《WebMCP 实战更新：让 AI 在网页里创作音乐、分析数据、修改页面》](https://cloud.tencent.com/developer/article/2767001)，作者"领航员"。文中可核对的点：

| 项目 | 内容 |
| --- | --- |
| 协议 | WebMCP，作者描述为 Chrome 浏览器原生 AI 工具协议 |
| 实验环境 | Chrome for Testing 151 |
| 作者自建的配套工具 | WebMCP Playground、调试用的 DevTools 插件 |
| 能做的事 | 在网页里创作音乐、分析数据、修改页面 |
| 作者结论句 | "WebMCP 的一个重要价值，是把 AI 接进用户已经打开的工作空间。" |

最后这句是整件事的重点。此前"AI 读网页"主要有两条路：抓取器把 HTML 拉回服务端做解析，或者浏览器插件把当前页面文本交给模型。两条路都是**把内容搬走再理解**。WebMCP 的差别在于：页面自己声明"我有这些能力、这些参数"，AI 在用户当前打开的页面里直接调用。

为了更完整地理解这个变化，可以把"AI 与网页的交互"分为三个阶段：

| 阶段 | 交互模式 | 代表技术 | 内容方需要做的 |
| --- | --- | --- | --- |
| 第一阶段：被动被读 | AI 抓取页面文本，离线解析 | 传统搜索引擎爬虫、GPT Browse | 确保 HTML 可抓取、正文可提取 |
| 第二阶段：主动插件 | 浏览器插件将当前页面交给 AI | Chrome AI 扩展、侧边栏助手 | 确保页面文本在无 CSS 时仍可读 |
| 第三阶段：双向调用 | 页面声明能力，AI 在页面内调用 | WebMCP、MCP 协议 | 结构化描述页面能力与参数 |

我们目前处于第一阶段向第二阶段过渡、第三阶段初现端倪的时期。WebMCP 的意义不在于它现在有多少用户在用，而在于它指出了内容方与 AI 之间的关系正在从"被读"走向"被调用"。

## 对做 GEO 的人来说，这换了个问题

过去的问法是："AI 抓到我了吗？读对了吗？"

新问法多了一层："**AI 能不能在我的页面上把事办成？**"

这不是科幻场景。用户已经越来越多地在对话里要求 AI 完成操作而不只是获取信息——查一个价格、按条件筛一批产品、把某段配置改成能用。如果页面只有散文式描述而没有可声明的能力与结构化字段，AI 只能读到"我们支持导出"，却没法真的导出。

对企业内容的影响可以拆成三层，前两层现在就能做：

**第一层：实体与字段命名规范化。** 页面里"套餐/版本/SKU/价格档位"要用同一套词，且每个值都有单位与条件。如果 AI 要把页面上的信息组装成一次调用，字段的歧义就是失败点。参考我们讲过的[实体一致性](/about/#五步做法)。

实体规范化的具体做法可以参照以下对照表：

| 不规范写法 | 规范化写法 | 为什么 |
| --- | --- | --- |
| "我们有好几种套餐" | "提供基础版、专业版、企业版三种套餐" | 明确数量和名称 |
| "价格从 99 元起" | "基础版月费 99 元（含税），年付 999 元" | 明确单位、周期、条件 |
| "支持多种格式导出" | "支持 CSV、Excel（.xlsx）、PDF 三种格式导出" | 明确枚举值 |
| "性能提升明显" | "TPOT 从 14.22ms 降至 7.8ms，下降 45.1%" | 用数字替代形容词 |

**第二层：把"能做什么"写成结构化段落。** 每页回答四个问题：这是什么、能做什么、需要什么前提、结果是什么。FAQPage 与 Product/Service 类型的 Schema 标记就是在做这件事，本站由 `scripts/seo.js` 在构建时写入。

四个问题的展开示例：

| 问题 | 回答要求 | 示例 |
| --- | --- | --- |
| 这是什么 | 一句话定义页面/产品 | "Qwen3.5-35B-A3B 是通义千问系列的 MoE 模型" |
| 能做什么 | 列出核心功能，每个功能独立一句 | "支持文本生成、代码补全、工具调用" |
| 需要什么前提 | 列出使用条件、环境要求 | "需要昇腾 910C 或同等级 GPU，显存 ≥ 64GB" |
| 结果是什么 | 给出可度量的效果 | "TPOT 在 c=1 条件下为 7.8ms" |

**第三层：真正提供可编程入口。** 有 API 或表单的产品，把参数、返回、限制写清楚（developer 类站点最容易做）。这一步对多数品牌站是长期项，但对工具类产品已经是竞争力。

这一层的核心是：让你的页面不只是一个信息载体，而是一个功能入口。当 AI 能在你的页面上直接完成"查价格→比配置→生成报价单"这样的链式操作时，你的页面就从"被引用"升级到了"被使用"——后者的用户粘性和商业价值远高于前者。

## 别把"能被调用"当营销话术

要提醒一件事：这个方向上现在没有任何"接入 WebMCP 就提升引用"的经验数据，我们也不做这种承诺。协议本身还处于早期实验（作者用的是 Chrome for Testing 通道，不是稳定版日常浏览器）。

我们把它收进视野的理由很实际：**内容结构化的收益路径正在从"摘录友好"扩展到"调用友好"**，而这两件事的准备动作高度重合。也就是说，现在为可读性做的改造，将来大概率也是为可调用性做的改造，投入不会白费。

以下是"摘录友好"与"调用友好"的对比：

| 维度 | 摘录友好 | 调用友好 |
| --- | --- | --- |
| 目标 | 让 AI 能正确引用你的内容 | 让 AI 能在你的页面上完成操作 |
| 内容形态 | 结构化文本、表格、FAQ | 结构化文本 + 可编程接口声明 |
| 技术基础 | HTML + Schema 标记 | HTML + Schema + API 描述 |
| 典型场景 | 品牌信息被 AI 回答引用 | 用户通过 AI 在你的页面下单、询价 |
| 当前成熟度 | 已有成熟实践 | 早期探索阶段 |
| 投入回报比 | 高（立即可做） | 中高（基础工作可复用） |

## 现在可以做的三个动作

1. 挑出你站点的 3 个核心任务页（下单、询价、开通），逐页检查：AI 只靠页面文本，能否判断"这一步该点什么、要填什么"。
2. 把关键参数从正文里提成表或定义列表。表格是被结构化解析摘走概率最高的形态。
3. 给这些页补 `dateModified` 与适用范围说明——调用出错时，能追回"当时页面上写的是什么"。

每个动作的具体执行建议：

| 动作 | 执行方式 | 验收标准 | 预计耗时 |
| --- | --- | --- | --- |
| 检查核心任务页 | 关闭 CSS 后逐页阅读纯文本 | 能仅凭文本理解页面功能 | 每页 10 分钟 |
| 参数表格化 | 将散落在正文中的参数提取为 `<table>` | 每个参数有名称、值、单位、条件 | 每页 15 分钟 |
| 补充 dateModified | 在 HTML `<head>` 或 Schema 中标注修改日期 | 日期精确到日，且随内容更新同步修改 | 全站 1 小时 |

## OneGeo 站怎么做

本站在内容结构化和"可调用友好"方面的实践：

| 做法 | 对应层次 | 实现方式 |
| --- | --- | --- |
| 实体一致性 | 第一层 | 同一概念全站统一用词，产品名/版本号/指标名不混用 |
| Schema 标记 | 第二层 | BlogPosting、FAQPage、Product 等结构化数据由构建脚本自动写入 |
| 参数表格化 | 第二层 | 所有性能数字、对比数据使用 `<table>` 标签而非段落 |
| 日期标注 | 第三层 | 每篇文章标注 `datePublished` 和 `dateModified` |
| 来源链接 | 第三层 | 每个引用数字附带可追溯的官方来源 |
| llms.txt | 第三层 | 提供站点级 AI 可读摘要文件，方便模型快速了解站点内容 |

这些做法的共同特点是：它们既服务于当前的"摘录友好"需求，也为未来的"调用友好"打下基础。当 WebMCP 或类似协议成熟时，已经做好结构化内容的站点可以无缝过渡，而从零开始的站点则需要补上所有基础功课。

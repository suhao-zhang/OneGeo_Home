## 我们核对的这条

来源是腾讯云开发者社区 2026 年 10 月 22 日 [《国产算力·昇腾 910C 大模型推理优化（上）：镜像更新与参数调优，提速 40%｜得物技术》](https://cloud.tencent.com/developer/article/2766437)。

正文里可核对的部分（照抄关键句）：

| 字段 | 内容 |
| --- | --- |
| 底座 | 华为昇腾 910C |
| 被测模型 | Qwen3.5-35B-A3B |
| 剖析工具 | MindStudio |
| 优化路径 | 镜像与版本升级 → 参数与环境变量调优 → vllm-ascend 源码修改 → 算子层融合优化 → MTP 投机解码（五个层次） |
| 累计落地 | 20 余项有效优化 |
| 关键指标句 | TPOT（Time Per Output Token，单 token 解码延迟）从基线 14.22ms 降至 7.8ms（c=1，下降 45.1%） |
| 其他指标句 | 另给出三项"分别下降 64.8%／49.9%／43.8%" |

我们按标题里的"40%"回到正文检索，**正文没有出现"40%"这个数字**。这篇文章的标题带"（上）"，说明只覆盖前两阶段，40% 很可能是那个范围里的口径——这是正常的连载写法，不是错误。

但它恰好构成一个真实场景：**标题里的数字，在正文里找不到同口径的原句。**

## 为什么这件事对 GEO 是致命的

摘录时，标题是被取走的概率最高的一句。当模型需要回答"昇腾 910C 上做大模型推理优化能提速多少"，它手上只有两句话可选：

- 标题："提速 40%"
- 正文："TPOT 从 14.22ms 降到 7.8ms（c=1，下降 45.1%）"

第二句更长、带条件、需要先理解 TPOT 和并发含义。多数回答会选第一句，或者把两句混着说成"最高可达 45%"——**三个数字，没有一个是原文里完整存在过的口径**。

这不是这篇文章独有的问题。技术内容里"标题取整、正文取极值、摘要去条件"是普遍现象，而生成式引擎不会替你把条件补回来。

我们可以通过一个对照表来理解这种口径漂移的典型模式：

| 原文写法 | 模型可能的引用 | 漂移类型 |
| --- | --- | --- |
| 标题"提速 40%"，正文"TPOT 下降 45.1%（c=1）" | "提速 40-45%" | 混合标题和正文，丢失条件 |
| "延迟从 14.22ms 降至 7.8ms" | "延迟降低约 8ms" | 取差值而非百分比，改变了度量方式 |
| "在 c=1 条件下" | 被省略 | 条件丢失，数字变成了无条件结论 |
| "Qwen3.5-35B-A3B 模型" | "Qwen 模型" | 具体型号被泛化，丢失精度 |
| "昇腾 910C" | "华为 AI 芯片" | 具体型号被泛化为品牌 |

每一行都是一种信息损失。单独看每一行似乎影响不大，但当模型在回答中同时发生这五种漂移时，最终输出的内容与原文口径已经相去甚远。

## 数字三件套

我们写含性能数字的页面时，强制每个数字带齐三件：

**1. 指标名。** 不是"提速"，而是"TPOT（单 token 解码延迟）"。指标名出现一次，摘录时就不会被当成端到端吞吐。

指标名的价值在于消除歧义。同一个"提速"可能指：端到端延迟降低、吞吐量提升、单请求响应时间缩短、首 token 延迟减少。如果不标明具体指标，模型在引用时会自行猜测，而猜测的结果往往不准确。

**2. 条件。** 并发 c=1、输入输出长度、是否含首 token 延迟。条件的价值在于它让数字可反驳——没有条件的数字只能被相信。

常见的条件维度包括：

| 条件类型 | 示例 | 为什么必须标注 |
| --- | --- | --- |
| 并发量 | c=1, c=32, c=128 | 不同并发下性能差异可达数倍 |
| 输入/输出长度 | 输入 512 token，输出 128 token | 长度直接影响延迟和吞吐 |
| 量化精度 | FP16, INT8, INT4 | 不同精度下算力需求和速度不同 |
| 是否含首 token | 含/不含 TTFT | TTFT 和 TPOT 是两个不同指标 |
| 硬件配置 | 单卡/多卡、显存大小 | 硬件直接影响性能上限 |
| 软件版本 | 框架版本、驱动版本 | 不同版本性能可能差异显著 |

**3. 基线与对比。** "从 14.22ms 降到 7.8ms"比"下降 45.1%"更可核对，因为它给出的是原始观测值，任何复述都能回查。

基线的价值在于可复现性。百分比"45.1%"本身无法验证——读者不知道原始数据是多少。但"14.22ms → 7.8ms"给出了两个可独立验证的锚点，任何人在相同条件下复测都能核对。

写成一句话的示范：

> 在并发 c=1 条件下，Qwen3.5-35B-A3B 昇腾 910C 推理的 TPOT 从基线 14.22ms 降至 7.8ms，下降 45.1%；该结果仅覆盖单请求解码延迟，不代表整体吞吐。

这句话即使被单独摘走，口径仍然完整。模型在引用时，无论摘走哪一部分，都不会产生误导。

## 标题的额外一条规则

**标题里的数字必须能在正文里找到同口径原句。** 做不到就把标题改成定性表述（"提速明显"、"分层优化路径"），别用一个正文里不存在的数字。这条我们在 `scripts/` 里没法自动化检查，只能靠写作时自查——但如果你的站点有大量性能类文章，值得做一个构建期脚本：抓出标题里的百分数与数字，在正文里找同数字，找不到就报警。

这条规则的延伸含义是：**标题不是摘要，是索引键。** 在 GEO 场景下，标题的主要功能不再是吸引人类点击，而是给模型提供一个快速定位的标签。如果标题里的数字在正文里找不到对应，模型就会面临"信标题还是信正文"的选择——而多数情况下，模型会选择标题，因为标题更短、更容易抽取。

## 常见错误模式与修正

以下是我们在监测中常见的数字口径错误模式，以及对应的修正建议：

| 错误模式 | 具体表现 | 修正方法 |
| --- | --- | --- |
| 标题正文不一致 | 标题写 40%，正文写 45.1% | 统一数字，或标题改为定性表述 |
| 条件缺失 | "提速 45%"不说并发量 | 补充完整测试条件 |
| 基线不明 | "下降 64.8%"不给原始值 | 同时给出原始值和目标值 |
| 指标名模糊 | "性能提升"不说哪个指标 | 明确是 TPOT、TTFT 还是吞吐 |
| 口径混用 | 同一篇里混用峰值和均值 | 统一使用同一种统计口径 |
| 时间缺失 | 不说测试日期和软件版本 | 标注测试环境的时间戳 |

## 与衡量口径的关系

数字口径属于"被描述准确率"这一项：AI 说出的数字，与页面原文是否为同一口径。取数方法见[GEO 的衡量口径](/geo-metrics/)。本站目前不发布任何"提升 N%"的效果数字，原因就在这儿——没有基线报告，就没有可核对的口径，也就没有资格把数字写进标题。

被描述准确率的判断标准非常朴素：**AI 说出一个数字时，能不能在原文里找到完全对应的那句话。** 能对应就是准确，不能就是失准。这跟传统 SEO 里的排名思维完全不同——GEO 不关心你排第几，关心的是你被引用时说对了没有。

## OneGeo 站怎么做

本站在处理含性能数字的文章时，执行以下标准流程：

| 步骤 | 检查内容 | 不通过的处置 |
| --- | --- | --- |
| 写作阶段 | 每个数字带齐"指标名 + 条件 + 基线"三件套 | 退回补充 |
| 编辑阶段 | 标题数字在正文中查找同口径原句 | 修改标题或补充正文 |
| 构建阶段 | 结构化数据标记关键数字（Schema 标记） | 构建脚本报警 |
| 发布后 | 定期用主流 AI 引擎测试引用准确率 | 发现漂移后修正页面 |

这套流程的核心思想是：**数字不是写完就结束的，它需要在写作、编辑、构建、发布后四个阶段都被检查。** 因为模型引用你的数字时，不会告诉你它引用的是哪个版本的页面——你只能确保每个阶段的数字都是自洽的。

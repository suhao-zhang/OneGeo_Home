## 两篇稿子里可核对的部分

来源是阿里云开发者社区同一个作者（GEO 信源实验室 / GEO 信源网）2026 年 9 月 18 日的两篇文章，我们于 10 月 26 日复核，两篇都仍可正常访问：

**[《GEO虚假信源正在泛滥，我们公开了第一批疑似风险渠道》](https://developer.aliyun.com/article/1764516)**（2026-09-18 17:56:55）

> "截至 2026 年 9 月 12 日，首批扫描已经识别出 306 台风险主机，覆盖 951 条在售媒体目录项。其中包括 263 个疑似 www 变体站群、25 个疑似仿冒品牌域名、12 个疑似冒用境外媒体名义的渠道，以及其他异常发布位。"

作者的处置方式也写了：不直接定义为"假媒体"，采用**疑似风险标记**，方法是"域名、媒体名称以及公开官方域名进行机械比对"，规则可复核、可重跑，误判可由媒体方提供备案、官方账号、编辑部联系方式申诉更正。名录开源在 GitHub（仓库名 `315fang/fake-geo-channels`）。作者的立场句是"GEO 不能继续依赖黑盒"，目标形态是"可查询、可验证、可复核的信源体系"。

**[《GEO文章发布后为什么仍可能失效？》](https://developer.aliyun.com/article/1764515)**（2026-09-18 17:54:43，标注 Lab Day 5）

原来的五层是 `Retrieve → Read → Use → Cite → Recommend`。作者在不同平台同步实验内容（官网、GitHub、知乎、CSDN、第三方博客）后发现同一篇内容在各平台的生命周期差别很大，于是补了更前一层：

`Survive → Retrieve → Read → Use → Cite → Recommend`，中文即"存活 → 召回 → 读取 → 使用 → 引用 → 推荐"。

他们由此得出的结论句我们非常认同：**"官网负责保存，第三方负责传播"、"第三方平台应该是放大器，而不是数据库"。**

## 这两件事和 OneGeo 的方法重合在哪

**其一，判定标准要能复核。** 我们只用三个口径——[被引用次数、被描述准确率、来源分布](/geo-metrics/)——每一条都是"逐题、逐模型、留证据"的方式，不做无法回查的断言。同行用"机械比对 + 疑似标记 + 可申诉"这套结构，价值就在**别人能重跑一遍得到同样结果**。行业里太多 GEO 报价单靠"收录率""AI 抓取权重"这类无法复核的黑盒词支撑，这类词我们自己从来不写。

**其二，Survive 是成本最高的一层，也是最容易被卖的一层。** 花钱发的第三方稿，控制权的四项都在别人手上：是否公开、URL 是否变化、账号是否存续、是否允许爬取。稿子被删之后，那笔预算对应的资产同时归零。

## 我们把 Survive 落成资产清单

按这条思路，本站把"信源"当资产管理，每条外部内容记五个字段：

| 字段 | 为什么要记 |
| --- | --- |
| URL | 唯一寻址，改名换路径都要留痕 |
| 发布平台与账号 | 判断控制权在谁手上 |
| 首次验证日期 / 最后验证日期 | 隔月复访，链接是否还打得开 |
| 是否有官网对应原始页 | 第三方消失时能否从自有站点恢复 |
| 口径版本号 | 与官网描述是否同一版，避免旧稿继续被引用 |

这张表的判据只有一条：**三年后这条 URL 还能不能打开，打开之后写的还是不是现在的口径。**答案不确定的，就把它归到"传播"而不是"资产"。

## 对仿冒域名这件事的态度

那份名录里的 263 个"www 变体站群"与 25 个"疑似仿冒品牌域名"，对企业是实打实的风险：站群把品牌名挂到内容上，模型学到的实体归属就乱了，严重时错误描述会长期留在语料里。企业侧可做的检查很朴素——

1. 搜一遍自己的品牌名 + "官网"，看结果里是否存在非自有主体的域名自称官网；
2. 核对自家域名的常见变体（有无 `www` 前缀、连字符、其他顶级域）是否在robots里明确处置，避免镜像与主站同时被收录；
3. 发现仿冒，除了法务动作，也应把线索提交给这类公开名录，让可复核的数据多一条。

本站的机器人策略与唯一规范地址写在 [robots.txt](/robots.txt) 与每页 canonical 里，就是为了让"哪个是原始出处"这件事不需要猜。

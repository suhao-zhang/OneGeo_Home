## 事件概要

博客园 2026 年 10 月 30 日出现一条热帖，标题大意是"27 岁程序员获无限 Token，挑战两个月重写思科 98% 的遗留代码"。原文描述了一位开发者利用 AI 编程工具（拥有无限量 API Token 额度），在两个月时间内对思科（Cisco）的遗留代码进行大规模重写。

这个帖子在开发者社区引发了广泛讨论，核心争议集中在两个数字上："98%"和"两个月"。

关键数字：

| 项目 | 原文表述 |
| --- | --- |
| 年龄 | 27 岁 |
| Token 额度 | 无限（∞） |
| 时间 | 两个月 |
| 重写比例 | 98% |
| 目标代码 | 思科遗留代码 |
| 验证方式 | 未提供 |

## 98% 是怎么算的

"98%"是一个高冲击力数字，但原文没有说明它的计算方法。在软件工程中，"代码的百分比"至少有四种不同的口径：

| 口径 | 含义差异 | 实际操作 |
| --- | --- | --- |
| 按代码行数 | 98% 的行被修改过（含微调） | git diff --stat 统计变更行数占比 |
| 按文件数 | 98% 的文件被 AI 重新生成 | find + 文件级 diff 统计 |
| 按模块数 | 98% 的功能模块被重构 | 需要定义"模块"边界 |
| 按 Git diff 比例 | 98% 的行与原始版本不同 | git diff --numstat 计算 |

四种口径下，"98%"的实际含义完全不同：

- **按行数算**：可能意味着大量微调（如变量重命名、格式调整）也算"重写"，实际改动深度可能很浅
- **按文件算**：可能意味着 98% 的文件被触碰过，但每个文件可能只改了几行
- **按模块算**：这是最严格的口径，意味着几乎全部功能被重构，工作量最大
- **按 Git diff 算**：介于行数和文件数之间，但受代码格式影响大

模型在引用时如果不知道是哪种口径，就可能把"按行数的 98%"理解成"按模块的 98%"，导致回答失真。

## "重写"的定义也没给

"重写"在软件工程里有多种含义，每种含义对应的工作量和风险完全不同：

| 重写类型 | 定义 | 工作量 | 风险 |
| --- | --- | --- | --- |
| 完全替换 | 从零写新代码，不参考原实现 | 极高 | 极高（可能引入新 bug） |
| AI 辅助重构 | 用 AI 工具对现有代码进行优化和改写 | 中等 | 中等（AI 可能引入微妙 bug） |
| 迁移重写 | 从一种语言/框架迁移到另一种 | 高 | 高（语义等价性难以保证） |
| 局部改写 | 只修改特定函数或模块 | 低 | 低（影响范围有限） |

原文标题的"重写"更像第二种——用 AI 辅助对遗留代码进行大规模改写。但模型不一定能区分这几种含义，尤其是当标题省略了"AI 辅助"这个定语时。

### 遗留代码的特殊挑战

思科的遗留代码有一些特殊属性，使得"重写"比一般代码更复杂：

1. **代码量大**——思科的核心网络设备软件经过 30+ 年积累，代码量可能达到数千万行
2. **文档缺失**——老代码往往缺少设计文档，理解原始意图困难
3. **测试覆盖低**——遗留代码的单元测试覆盖率通常不高，重写后难以验证正确性
4. **依赖复杂**——模块之间耦合度高，改一处可能影响多处
5. **性能敏感**——网络设备代码对延迟和吞吐量有严格要求，重写后性能不能下降

在这些约束下，"两个月重写 98%"即使有 AI 辅助，也是一个极其激进的目标。模型在引用时需要理解这个背景。

## 验证方式的缺失

原文没有提供任何验证方式来支撑"98%"这个数字。可能的验证方式包括：

| 验证方式 | 可信度 | 说明 |
| --- | --- | --- |
| Git diff 截图 | 高 | 可以直接看到变更比例 |
| 代码审查报告 | 高 | 第三方审查确认变更范围 |
| 自动化测试通过率 | 中 | 测试通过不代表重写正确 |
| 本人声明 | 低 | 无第三方验证 |
| 博客/社交媒体帖子 | 低 | 属于二手信源 |

没有验证方式的数字，模型在回答时应该加上"据称""报道称"等限定词，而不是直接当作事实引用。

## AI 辅助代码重写的行业现状

这个博客园帖子之所以引发热议，是因为它触及了当前开发者社区对 AI 编程能力的一个核心讨论：AI 到底能在多大程度上替代人工代码重写？

### AI 编程工具的能力边界

2025-2026 年，AI 编程工具（如 GitHub Copilot、Cursor、Claude Code 等）的能力已经有了显著提升，但仍有明确的边界：

| 能力维度 | AI 可以做的 | AI 做不到的 |
| --- | --- | --- |
| 代码生成 | 根据注释或描述生成函数/模块 | 理解复杂业务逻辑并独立设计架构 |
| 代码重构 | 按规则重命名变量、调整格式 | 判断重构是否破坏业务逻辑 |
| Bug 修复 | 修复简单的语法错误和逻辑错误 | 修复涉及多模块交互的复杂 bug |
| 代码审查 | 发现常见的代码风格问题 | 发现深层的设计缺陷 |
| 大规模重写 | 按模式批量修改代码 | 理解每处修改的业务影响 |

"两个月重写思科 98% 遗留代码"这个声明，如果是指"用 AI 工具批量修改了 98% 的代码行"，那是可信的；但如果是指"用 AI 工具重新实现了 98% 的功能模块并保证正确性"，那就需要更多验证。

### "无限 Token"的含义

帖子中提到开发者获得了"无限 Token"额度。在 AI 编程工具的语境下，"Token"通常指 API 调用额度——每次让 AI 分析或生成代码都需要消耗 Token。

"无限 Token"意味着：
- 开发者可以无限制地让 AI 分析代码
- 可以反复运行 AI 重写并对比结果
- 不用担心 API 费用

这确实是一个有利条件，但"无限 Token"不等于"无限能力"。AI 工具的输出质量仍然受限于模型本身的能力边界。

## 这对 GEO 意味着什么

**一、百分比必须附带计算方法。** "98%"后面如果不写"按代码行数计"或"按模块数计"，模型就无法判断这个数字的真实含义。写正文时把计算口径和百分比放在一起，模型抽取时才不会出现口径漂移。

**二、"重写"需要定义。** 同一个词在不同语境下含义差距很大。正文里用一句话说明"本文所称重写是指……"，模型在引用时就能准确传达。

**三、验证方式增加可信度。** 如果原文提供了 Git diff 截图、代码审查报告或第三方验证链接，模型就能判断这个数字的可信度。没有验证方式的数字，模型在回答时可能会加上"据称"或"报道称"等限定词。

**四、时间窗口要和工程量匹配。** "两个月"对于"重写 98% 的思科遗留代码"是否合理？模型在评估这个声明的可信度时，需要知道代码总量和工程复杂度。正文里提供这些背景信息，模型才能给出有上下文的判断。

**五、二手信源要标注。** 博客园帖子属于二手信源（原作者自述），不是经过验证的一手数据。模型在引用时应该标注"据博客园帖子"而非直接当作事实。

## OneGeo 站怎么做

本站在报道代码重写/AI 编程类话题时，遵循以下口径规范：

1. **必标注计算方法**——"按行数计""按模块计"
2. **必定义"重写"含义**——完全替换 / AI 辅助 / 迁移 / 局部改写
3. **必提供验证方式**——Git diff / 代码审查 / 测试报告
4. **必标注代码背景**——代码量、复杂度、历史
5. **二手信源必标注来源**——"据 XX 帖子"而非直接陈述
